# 章节写作规范

从本课程正式编写正文开始，每一章必须严格遵守本规范。

---

## 0. 章节分类

本教材章节分为三类，作者动笔前必须先判定本章属于哪类。

| 类型 | 说明 | 典型章节 |
|---|---|---|
| **A 类：工具/环境章** | 以安装、配置、搭建环境为主 | 环境安装、Git 配置、集群搭建、工具链初始化 |
| **B 类：概念/原理章** | 以理解架构、机制、底层原理为主 | 容器原理、K8s 网络模型、Controller 控制循环、OCI 规范 |
| **C 类：实践/开发章** | 以编写代码、配置、部署、调试为主 | Go Web API、Dockerfile、Helm Chart、Kubebuilder 开发 |

不同类型对应不同的必填/选填要求（见各节标注）。

---

## 章节固定结构

全章按以下顺序组织。标注"必填"的节所有类型都必须写；标注"B/C 类必填"的节 A 类可省略；标注"C 类必填"的节 A/B 类可省略。

```markdown
# 章节标题

## 1. 本章学习目标（必填）

## 2. 本章工作场景与真实案例（必填）

## 3. 核心概念（必填）

## 4. 原理深入（B/C 类必填，A 类选填）

## 5. 手把手实验（必填）

## 6. 常见错误与排障（B/C 类必填，A 类选填）

## 7. 生产环境注意事项（B/C 类必填，A 类选填）

## 8. 本章小项目（必填）

## 9. 本章练习题（必填）

## 10. 本章面试题（B/C 类必填，A 类选填）

## 11. 本章总结（必填）

## 12. 下一章衔接（必填）
```

## 1. 本章学习目标

说明学完本章后，学习者应该掌握什么。

必须区分两类目标：

- **知识目标**（能解释/能描述/能对比）：学完本章后，学习者能解释______、能描述______、能对比______
- **技能目标**（能独立完成/能排查/能配置）：学完本章后，学习者能独立完成______、能排查______、能配置______

要求：

- 每章至少 2 条技能目标
- 目标要具体，可以被检查（避免"了解""熟悉"等不可验证的动词，使用"能写出""能部署""能定位""能解释"）
- 目标要和真实岗位能力有关
- 目标要和最终项目主线有关

示例（Dockerfile 章节）：

```
知识目标：
- 能解释多阶段构建的原理和好处
- 能对比 COPY 与 ADD 指令的差异和使用场景

技能目标：
- 能独立为 Go 服务编写生产可用的多阶段 Dockerfile
- 能通过 .dockerignore 和构建缓存优化镜像构建速度
- 能配置非 root 用户运行容器
```

## 2. 本章工作场景与真实案例

本节合并了"工作场景"和"真实案例"，按以下三层组织：

**2.1 技术痛点**

说明这个技术解决什么问题。不用会怎样？以前是怎么做的？

**2.2 团队协作场景**

说明开发、测试、运维分别如何使用这个技术，职责边界是什么。

**2.3 课程项目关联**

说明本节内容如何应用到 **Cloud Native Todo Platform** 的哪个阶段。

要求：

- 痛点必须具体，禁止只写"提高效率""方便管理"等空泛表述
- 协作场景必须说明谁写、谁审、谁部署、出问题谁处理
- 项目关联必须指出本章实验产出会被后续哪几章复用

---

## 3. 核心概念

用新手能理解的方式解释概念，但不能过于浅显。

**三步法**：

1. **是什么**：一句话定义，让零基础读者也能理解
2. **为什么需要它**：它解决了什么问题，没有它之前是怎么做的
3. **在项目中怎么用**：给出一个最小示例，关联到课程项目

要求：

- 必须包含可运行的示例代码或配置
- 本节聚焦**静态知识**（结构、字段含义、YAML 怎么写、类型定义）
- 与第 4 节的边界：第 3 节讲"是什么"，第 4 节讲"怎么运转的"

---

## 4. 原理深入

讲清楚底层原理、运行机制、关键流程。

要求：

- 本节聚焦**动态过程**（组件之间如何交互、数据如何流动、状态如何变化）
- 不停留在命令表面
- 解释关键组件之间的关系
- 对 Docker、Kubernetes、Operator 等章节必须包含运行流程图
- 与第 3 节的边界：第 3 节讲"静态结构"，第 4 节讲"动态过程"

---

## 5. 手把手实验

每章必须有完整实验。按以下八步组织：

| 步骤 | 内容 | 要求 |
|---|---|---|
| 1. 实验目标 | 本次实验要达成什么 | 一句话，可验证 |
| 2. 实验环境 | 需要的软件和版本 | 列出具体版本号 |
| 3. 文件目录结构 | 实验涉及的文件 | 用 tree 命令输出 |
| 4. 完整代码或配置 | 所有代码和 YAML | 完整可运行，关键字段有注释 |
| 5. 执行命令 | 按顺序执行的命令 | 每行命令解释为什么执行 |
| 6. 预期输出 | 命令的预期结果 | 贴真实终端输出，过长部分用 `...` 省略 |
| 7. 验证方法 | 如何确认实验成功 | 给出检查命令和判断标准 |
| 8. 清理步骤 | 如何恢复环境 | 避免残留资源占用 |

要求：

- 所有代码尽量完整可运行（新手可以一步步复现，不依赖未提供的文件）
- 所有 YAML 必须解释关键字段
- 不能省略任何步骤
- **末尾标注预计耗时**：

```
预计耗时：45 分钟（动手操作约 30 分钟）
```

## 6. 常见错误与排障

对每个常见错误，按以下闭环格式组织：

```markdown
### 错误 1：[错误名称]

- **现象**：贴真实报错信息或异常行为（不要只描述，要贴输出）
- **原因**：为什么会发生
- **排查**：用什么命令定位

  ```bash
  排查命令
  # ← 关键输出解读
  ```

- **修复**：具体操作步骤
- **预防**：如何避免再次发生
```

要求：

- 每章至少 2 个，最多 5 个常见错误
- 错误必须来自真实开发/运维场景，不要编造不会发生的错误
- 现象必须包含可识别的关键词（如 `CrashLoopBackOff`、`dial tcp: connection refused`），方便学习者搜索
- 排查命令必须解释输出怎么看（不能只贴输出不解释）

---

## 7. 生产环境注意事项

说明生产环境中需要注意的稳定性、安全性、性能和可维护性问题。

要求：

- 不只讲开发环境
- 必须考虑真实上线风险
- 涉及 Kubernetes 时必须关注资源、权限、网络、安全、回滚
- 每条约 100-200 字，3-5 条
- **A 类章如确实没有生产环境概念（如 Git 配置、Shell 脚本基础），本节可省略，但需在第 11 节总结中注明原因**

---

## 8. 本章小项目

每一章都必须有一个小项目，项目要符合本章主题。

要求：

- 小项目必须能独立验收（学习者完成后的产出可以被客观检查）
- 小项目必须服务于最终项目主线 **Cloud Native Todo Platform**
- 每章成果要能被后续章节复用或演进
- 验收标准必须明确：完成什么操作、观察到什么结果、得到什么产出

---

## 9. 本章练习题

必须包含三个层次：

| 层次 | 数量 | 说明 |
|---|---|---|
| 基础题 | 3-5 道 | 检查概念理解，形式不限（选择/填空/简答） |
| 实操题 | 2-3 道 | 要求动手操作，每道题有明确的验收标准 |
| 思考题 | 1-2 道 | 开放性问题，连接真实工作场景，无标准答案 |

要求：

- 基础题检查概念（不是考记忆力，是考理解）
- 实操题检查动手能力（每道题必须有验收标准："当你看到______时，说明操作成功"）
- 思考题连接真实工作场景（"如果你的同事______，你会怎么排查？""如果并发量提高 10 倍，现有方案哪里会出问题？"）

---

## 10. 本章面试题

给出常见面试问题和参考答案。

要求：

- 每章至少 3 道（B/C 类）
- 问题要贴近真实面试（不是课后习题的简单变体）
- **答案必须分层**：

```markdown
### 面试题：______

**一句话结论**：（20 秒版本，面试官第一印象）

**展开解释**：（2 分钟版本，展示理解的深度）

**深入追问**：（如果面试官继续追问，你能答到什么程度）
```

- 不能只有背诵式定义（面试官反感"八股文"式回答）
- 追问部分可以超出本章范围但仍在课程能力边界内

---

## 11. 本章总结

总结本章核心内容。

三段式：

1. **知识回顾**：本章学了哪 3-5 个关键知识点
2. **项目成果**：本章小项目的产出是什么，在整体项目中的位置
3. **能力价值**：学完本章，你能胜任工作中的什么任务

字数控制在 200-300 字。

---

## 12. 下一章衔接

说明本章如何衔接下一章。

要求：

- 指明本章的哪些产出（代码、配置、环境、概念理解）会被下一章直接使用
- 说明下一章为什么需要本章的知识基础——如果跳过本章直接学下一章会卡在哪里
- 如本章内容暂时不被后续章节直接使用（例：独立的工具介绍），说明其在完整知识体系中的位置
- 2-3 句话即可，不要写成下一章的预告

## 附录 A：代码与配置格式规范

### A.1 代码块

```
1. 所有代码块必须用三个反引号标注语言类型：
   ```go
   ```yaml
   ```bash
   ```shell
   ```dockerfile
   ```json
   ```text

2. 禁止不标注语言的无类型代码块

3. 代码块内的注释使用该语言的注释语法，不要用中文解释替代代码注释
```

### A.2 Shell 命令

```
1. Bash 命令不使用 `$` 或 `#` 提示符，保证代码块可以直接复制执行
2. 需要 root 权限的命令直接写 `sudo ...`
3. 命令和输出分开为两个代码块，或明确标注"输出："
4. 输出过长时用 ... 省略非关键部分，并标注省略了什么
5. 每条命令前用一句话解释执行目的
6. 连续多条命令如无依赖关系，用独立代码块分别展示
7. 示例：

   查看 Pod 状态：
   ```bash
   kubectl get pods -n todo-app
   ```
   预期输出：
   ```text
   NAME                        READY   STATUS    RESTARTS   AGE
   todo-api-7d8f6c9b5-x2k4j   1/1     Running   0          30s
   ```
```

### A.3 YAML 配置

```
1. 关键字段必须带行内注释（使用 # ← 箭头指向格式，与代码注释区分）：

   ```yaml
   spec:
     replicas: 3            # ← 生产环境建议 3 副本
     strategy:
       type: RollingUpdate  # ← 滚动更新，避免停机
   ```

2. 超过 50 行的 YAML 在开头用注释标注结构概览
3. 敏感值用占位符：<your-password>、<your-token>、<your-domain>
4. 缩进统一用 2 空格（Kubernetes YAML 惯例）
```

### A.4 Go 代码

```
1. 所有 Go 代码必须通过 gofmt 格式化
2. import 分组：标准库 / 第三方库 / 项目内部包，用空行分隔
3. 示例代码中的错误处理不能省略（教学代码不是原型代码）
4. 公共函数和类型必须有注释（符合 godoc 惯例）
```

### A.5 路径与文件名

```
1. 文件和路径使用等宽字体：/etc/kubernetes/manifests/
2. 禁止出现真实绝对路径（/home/alice/projects/），使用 <project-root> 占位
3. 项目根目录统一用 <project-root> 表示
```

## 附录 B：术语一致性规范

### B.1 技术名词

| 规范写法 | 禁止写法 |
|---|---|
| Pod | pod, POD |
| Kubernetes | k8s, K8S, K8s（仅限标题可简写） |
| Deployment | deployment, deploy |
| etcd | Etcd, ETCD |
| ConfigMap | configmap, configMap |
| Namespace | namespace（代码/命令中除外） |
| Docker | docker（句首除外） |
| Go | go, golang（正式正文中） |
| Redis | redis |
| PostgreSQL | postgresql, postgres, pg（首次出现可用"PostgreSQL"） |

### B.2 缩写处理

```
1. 每个技术缩写首次出现时必须标注全称：
   CRI（Container Runtime Interface，容器运行时接口）
   CRD（Custom Resource Definition，自定义资源定义）

2. 同一章内第二次出现可直接用缩写

3. 章节标题中优先使用全称，如过长可用缩写
```

### B.3 命令、标志、字段名

```
1. 命令行工具、子命令、标志、API 字段名使用等宽字体：
   kubectl get pods -n default
   imagePullPolicy: Always

2. Kubernetes 资源类型作为代码引用时首字母大写等宽字体：
   Deployment、Service、ConfigMap
```

```

## 额外写作原则

1. 不要只给概念，必须有示例。每个抽象概念后面紧跟一个具体示例。
2. 不要只给命令，必须解释命令背后的原因——"为什么执行这条命令"比"这条命令是什么"更重要。
3. 不要只给 YAML，必须解释每个关键字段——用 `# ←` 箭头注释标注。
4. 不要省略安装、启动、验证和清理步骤——实验必须有始有终。
5. 所有代码必须在本机完整验证过——不能有"理论上可以运行"的代码。
6. 所有章节要围绕最终综合项目逐步铺垫——每章的产出必须在后续章节中被使用。
7. 写作风格：清晰 > 优美，具体 > 抽象，能跑 > 能看。
8. 用初学者的视角重读——你不写的假设，学习者就不会知道。
